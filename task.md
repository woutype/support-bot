# 📋 ТЕХНИЧЕСКОЕ ЗАДАНИЕ (ТЗ)
## Проект: «SupportDesk Bot» — Асинхронный сервис технической поддержки

> **Стек:** Python 3.11+ | aiogram 3.x | asyncpg (PostgreSQL) | python-dotenv

---

## 1. Назначение и концепция сервиса

Сервис предназначен для организации двусторонней службы технической поддержки в Telegram между **Клиентами (пользователями)** и **Операторами поддержки (администраторами)**. 

### Ключевая ценность:
1. Клиент получает удобный канал связи без необходимости звонить или ждать на линии.
2. Оператор работает через единый интерфейс с интерактивными кнопками прямо в Telegram.
3. Все обращения и ответы логируются в реляционной базе данных со статусами и временными метками.

## 3. Схема базы данных (Database Schema)

### Таблица 1: `users` (Пользователи)
| Колонка | Тип данных | Ограничения | Описание |
| :--- | :--- | :--- | :--- |
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Внутренний ID записи |
| `tg_id` | BIGINT | UNIQUE NOT NULL | Telegram ID пользователя |
| `username` | TEXT | NULLABLE | Никнейм пользователя (@username) |
| `full_name` | TEXT | NOT NULL | Имя и фамилия в Telegram |
| `created_at` | TIMESTAMP | DEFAULT CURRENT_TIMESTAMP | Время первой регистрации |

### Таблица 2: `tickets` (Обращения)
| Колонка | Тип данных | Ограничения | Описание |
| :--- | :--- | :--- | :--- |
| `id` | INTEGER | PRIMARY KEY AUTOINCREMENT | Уникальный номер обращения (#1, #2...) |
| `user_tg_id` | BIGINT | NOT NULL, REFERENCES users(tg_id) | ID автора обращения |
| `issue_text` | TEXT | NOT NULL | Текст проблемы клиента |
| `status` | TEXT | NOT NULL DEFAULT 'OPEN' | Статус: `OPEN`, `ANSWERED`, `CLOSED` |
| `admin_tg_id` | BIGINT | NULLABLE | ID админа, взявшего в работу/ответившего |
| `admin_reply` | TEXT | NULLABLE | Текст ответа службы поддержки |
| `created_at` | TIMESTAMP | DEFAULT CURRENT_TIMESTAMP | Дата создания тикета |
| `updated_at` | TIMESTAMP | DEFAULT CURRENT_TIMESTAMP | Дата ответа или закрытия |

## 4. Сценарии событий и шаблоны сообщений

### 4.1. Сценарии пользователя (Клиента)

#### Событие 1.1: Команда `/start` (Первый запуск или перезапуск)
* **Триггер:** Пользователь отправляет команду `/start`.
* **Логика бэкенда:** 
  1. Выполняется `INSERT OR IGNORE INTO users ...`
  2. Выводится приветствие и главное меню.
* **Шаблон сообщения:**
  ```text
  👋 Здравствуйте, {full_name}!

  Добро пожаловать в службу технической поддержки.
  Здесь вы можете задать вопрос специалистам или сообщить о технической проблеме.

  Нажмите кнопку ниже, чтобы создать обращение.
  ```
* **Клавиатура (Reply):**
  * `[ 🎫 Создать обращение ]`
  * `[ 📋 Мои обращения ]`

---

#### Событие 1.2: Нажатие кнопки «🎫 Создать обращение»
* **Триггер:** Клиент нажал кнопку «Создать обращение» или ввел `/ticket`.
* **Логика бэкенда:**
  1. Бот переводит пользователя в состояние `TicketCreateState.waiting_for_text`.
  2. Выводится инструкция с кнопкой отмены.
* **Шаблон сообщения:**
  ```text
  📝 Опишите вашу проблему подробно в одном сообщении.

  Если нужно, укажите номер счета, код ошибки или детали ситуации. 
  Для отмены нажмите кнопку «❌ Отмена» ниже.
  ```
* **Клавиатура (Reply):**
  * `[ ❌ Отмена ]`

---

#### Событие 1.3: Пользователь нажал «❌ Отмена»
* **Триггер:** Сообщение «❌ Отмена» или `/cancel` в состоянии ввода.
* **Логика бэкенда:**
  1. Сброс состояния FSM (`await state.clear()`).
  2. Возврат главного меню.
* **Шаблон сообщения:**
  ```text
  🚫 Создание обращения отменено. Вы возвращены в главное меню.
  ```

---

#### Событие 1.4: Пользователь отправил текст обращения
* **Триггер:** Текстовое сообщение в состоянии `TicketCreateState.waiting_for_text`.
* **Логика бэкенда:**
  1. Валидация: длина текста не менее 5 символов и не более 2000 символов.
  2. Запись в БД: `INSERT INTO tickets (user_tg_id, issue_text, status) VALUES (...) RETURNING id`.
  3. Сброс состояния FSM.
  4. Отправка подтверждения пользователю.
  5. Отправка карточки тикета администратору в чат поддержки.
* **Шаблон сообщения пользователю:**
  ```text
  ✅ Ваше обращение #{ticket_id} успешно зарегистрировано!

  Специалист службы поддержки уже получил уведомление и ответит вам в ближайшее время прямо в этот чат.
  ```

---

#### Событие 1.5: Просмотр списка своих тикетов («📋 Мои обращения»)
* **Триггер:** Клиент нажал «📋 Мои обращения» или ввел `/mytickets`.
* **Логика бэкенда:**
  1. Запрос в БД: `SELECT * FROM tickets WHERE user_tg_id = ? ORDER BY id DESC LIMIT 5`.
* **Шаблон сообщения (если обращений нет):**
  ```text
  📭 У вас пока нет созданных обращений.
  ```
* **Шаблон сообщения (если есть обращения):**
  ```text
  📋 Ваши последние обращения:

  • Тикет #14 [🟢 Открыт]:
    «Завис платеж на сумму 500 BYN...»

  • Тикет #9 [✅ Решен]:
    «Не приходит SMS-код...»
    ↳ Ответ поддержки: «Проблема решена, повторите запрос.»
  ```

### 4.2. Сценарии администратора (Специалиста поддержки)

#### Событие 2.1: Мгновенное уведомление о новом тикете
* **Триггер:** Успешная запись нового тикета в базу данных.
* **Получатель:** `ADMIN_ID` (из `.env`).
* **Шаблон сообщения админу:**
  ```text
  🔔 НОВОЕ ОБРАЩЕНИЕ #{ticket_id}
  ━━━━━━━━━━━━━━━━━━━━
  👤 От: {full_name} (@{username} | ID: <code>{user_tg_id}</code>)
  ⏰ Время: {created_at}

  📄 Содержание:
  «{issue_text}»
  ━━━━━━━━━━━━━━━━━━━━
  Статус: 🟡 Ожидает ответа
  ```
* **Инлайн-клавиатура (Inline):**
  * `[ ✍️ Ответить ]` — `callback_data="reply_ticket:{ticket_id}"`
  * `[ ❌ Закрыть без ответа ]` — `callback_data="close_ticket:{ticket_id}"`

---

#### Событие 2.2: Админ нажимает инлайн-кнопку «✍️ Ответить»
* **Триггер:** Нажатие кнопки с `callback_data="reply_ticket:{ticket_id}"`.
* **Логика бэкенда:**
  1. Проверка: не закрыт ли тикет другим оператором (`SELECT status FROM tickets WHERE id = ?`).
  2. Сохранение `ticket_id` и `user_tg_id` в FSM администратора (`AdminReplyState.waiting_for_reply`).
  3. Отправка подтверждения клика через `callback.answer()`.
* **Шаблон сообщения админу:**
  ```text
  ✍️ Введите текст ответа для обращения #{ticket_id}:
  (Клиент получит ваше сообщение от имени бота. Для отмены отправьте /cancel).
  ```

---

#### Событие 2.3: Админ отправляет текст ответа
* **Триггер:** Сообщение от админа в состоянии `AdminReplyState.waiting_for_reply`.
* **Логика бэкенда:**
  1. Выполняется SQL:
     ```sql
     UPDATE tickets 
     SET status = 'ANSWERED', admin_reply = ?, admin_tg_id = ?, updated_at = CURRENT_TIMESTAMP 
     WHERE id = ?;
     ```
  2. Отправка сообщения клиенту в личный чат Telegram по `user_tg_id`.
  3. Редактирование исходной карточки тикета у админа (смена статуса на «Решено»).
  4. Сброс FSM админа.
* **Шаблон сообщения клиенту:**
  ```text
  📩 Получен ответ службы поддержки по обращению #{ticket_id}:
  ━━━━━━━━━━━━━━━━━━━━
  «{admin_reply_text}»
  ━━━━━━━━━━━━━━━━━━━━
  Если у вас остались вопросы, вы всегда можете создать новое обращение.
  ```
* **Шаблон обновленной карточки у админа:**
  ```text
  🔔 ОБРАЩЕНИЕ #{ticket_id} (ОБРАБОТАНО)
  ━━━━━━━━━━━━━━━━━━━━
  👤 От: {full_name} (@{username})
  📄 Вопрос: «{issue_text}»
  ━━━━━━━━━━━━━━━━━━━━
  ✅ Ответ отправлен:
  «{admin_reply_text}»
  ```

---

#### Событие 2.4: Админ нажимает «❌ Закрыть без ответа»
* **Триггер:** Нажатие кнопки с `callback_data="close_ticket:{ticket_id}"`.
* **Логика бэкенда:**
  1. SQL-запрос: `UPDATE tickets SET status = 'CLOSED' WHERE id = ?;`.
  2. Уведомление клиента о закрытии тикета.
  3. Удаление инлайн-кнопок из сообщения у админа.
* **Шаблон сообщения клиенту:**
  ```text
  ℹ️ Ваше обращение #{ticket_id} было закрыто специалистом поддержки.
  ```

## 5. Обработка исключений и граничных случаев (Edge Cases)

1. **Пользователь заблокировал бота:**
   * При попытке отправки ответа клиенту ловится исключение `TelegramForbiddenError` (Бот заблокирован).
   * Админу выводится алерт: `⚠️ Не удалось доставить ответ: пользователь заблокировал бота`. Статус тикета помечается как `FAILED_DELIVERY`.
2. **Слишком длинный текст:**
   * Telegram имеет лимит в 4096 символов на сообщение. Текст обращения валидируется (макс. 2000 символов), чтобы избежать падений API.
3. **Безопасность админ-панели:**
   * Все хэндлеры админа защищены кастомным фильтром `IsAdmin(admin_id)`. Обычный пользователь не может сымитировать callback-запрос.
